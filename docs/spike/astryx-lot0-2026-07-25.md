## 3. API gaps rencontrés (Q7 détaillée)

| # | Gap | Composant | Contournement | Coût |
|---|---|---|---|---|
| 1 | Variants `outline`/`link` absents | Button | cva porte le style, Astryx reçoit `variant="primary"` | wrapper résiduel |
| 2 | 3 sizes (sm/md/lg) vs 8 shadcn | Button | cva porte toute la scale | wrapper résiduel |
| 3 | Pas d'elevation/shadow natif | Card | className utilitaire `shadow-float` | trivial |
| 4 | `label: string` obligatoire (a11y) | Button | `deriveLabel(children)` + fallback "Bouton" | wrapper |
| 5 | `SpacingStep` non réexporté depuis `Card` subpath | Card | déclaré localement (union littéral identique) | trivial |
| 6 | Pattern Base UI `render` non supporté | Button | `cloneElement` injecte classes + data-slot | wrapper lourd |

**Bilan** : 6/6 contournables, mais 3 d'entre eux (variants, sizes, render) exigent que le wrapper shadcn conserve sa cva complète. Autrement dit : **Astryx Button/Card deviennent des coquilles vides derrière la cva shadcn existante**. Le bénéfice d'une migration full-Astryx (utiliser `<Button label="…" variant="primary" />` natif) ne s'applique pas — la grammaire Airbnb est trop spécifique pour être exprimée via l'API Astryx seule.

## 6. Décision

### **AMBER — ne pas engager la migration complète maintenant**

**Raisons** :
1. **Q7 beta** : 6 API gaps sur 2 composants (seuil ≤2 dépassé). Tous contournables mais le pattern de contournement dominant = **garder la cva shadcn** comme source de vérité stylistique, Astryx devient un simple remplaçant de primitive Base UI. Le bénéfice attendu (API Astryx déclarative, xstyle, moindre maintenance) ne se matérialise pas.
2. **Cohérence** : le thème Airbnb (Rausch, tokens métier ferme/planifie/suggere, 2 shadow tiers) est *trop spécifique* pour la grammaire générique d'Astryx. Les tokens custom finissent en CSS scope statique — ils auraient pu rester dans `app.css` directement.
3. **Bundle** : +54 KB gz est acceptable mais n'apporte aucune fonctionnalité nouvelle tant que cva shadcn reste la source stylistique.
4. **Pages intactes** : aucune page de production migrée. Le risque est contenu. C'est aussi la limite du spike : il ne prouve pas que Astryx *améliore* l'expérience — seulement qu'il *coexiste*.

### Conditions pour passer à GO

L'une de ces trois voies :
- **(A) Attendre Astryx 1.0 stable** : si la 1.0 élargit l'API variants/sizes ou fournit un codemod shadcn → Astryx, le coûtwrapper baisse.
- **(B) Cherry-picker les composants différenciants** : migrer uniquement les composants où Astryx apporte une vraie valeur au-delà de shadcn — typiquement `AppShell` (layout global), `Table` (virtualisation native), `Form` wizards, `@astryxdesign/charts`. Garder shadcn pour le reste. Approche hybride.
- **(C) Re-thématiser sur un thème Astryx prêt** : si on accepte d'abandonner la grammaire Airbnb maison au profit d'un thème Astryx officiel (neutral/butter), l'effort wrapper tombe mais c'est une refonte visuelle produit — décision métier, pas technique.

### Recommandation immédiate

- **Garder la branche `refacto-astryx`** comme preuve de faisabilité (spike archivé).
- **Ne pas merger** sur master — la page `/astryx-lab` est un artefact de spike, pas une feature produit.
- **Documenter la décision** dans l'issue #90 (commentaire) : AMBER, voies A/B/C ci-dessus.
- **Suivre Astryx** : watcher les releases 0.2.x / 1.0 sur npm pour réévaluer quand l'API mûrit.
